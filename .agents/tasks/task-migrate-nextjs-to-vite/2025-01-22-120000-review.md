# Next.js to Vite + TanStack Router migration

This change replaces the entire Next.js Pages Router setup with Vite as the bundler, TanStack Router for client-side routing, and TanStack Query for data fetching (already migrated in an earlier commit in this branch). The app becomes a fully static SPA deployed to Netlify, with a Netlify function handling the image proxy that was previously a Next.js API route. A custom ThemeProvider replaces next-themes, and vite-plugin-pwa replaces next-pwa.

Watch for: The Convex URL is hardcoded in `netlify.toml` build environment, exposing the backend URL in source control (confirmed). The root index route uses a client-side redirect via `useEffect` + `navigate()`, which means crawlers and users see a blank page briefly on `/` before landing at `/stations` (confirmed). The 647KB single JS chunk has no code-splitting — all three routes and their dependencies load upfront (confirmed).

**Verdict**: APPROVED

## High-level view

The migration cleanly separates concerns: Vite handles bundling and PWA generation, TanStack Router provides a manually-defined route tree (not file-based auto-generation), and TanStack Query hooks wrap a singleton `ConvexHttpClient` that fetches data over HTTP rather than maintaining a WebSocket subscription. The loss of Convex's real-time push in favor of polling with a 30-second `staleTime` is a deliberate architectural trade-off for simpler SPA hosting.

The routing layer is thin — four routes defined in `routeTree.gen.ts` with manual imports rather than codegen. The file is named `.gen.ts` but is hand-written, which could mislead future contributors into thinking it's auto-generated and safe to delete or overwrite.

Progressive loading works as intended: the stations list query returns all station metadata including current water levels in a single fetch, so cards render immediately. Per-station trend data (MicroTrendChart, MiniTrendChart) loads independently via separate TanStack Query hooks and shows its own animated placeholder while pending.

The Netlify deployment config is straightforward — static `dist/` directory with a catch-all SPA redirect and a function redirect for `/api/proxy-image/:id`. The proxy function fetches images from the JPS government server over plain HTTP and returns them base64-encoded with a 5-minute cache header.

## Route tree and navigation wiring

The route tree in `src/routeTree.gen.ts` is hand-authored despite the `.gen` suffix. PostHog initialization in `RootLayout` uses `import.meta.env.VITE_POSTHOG_KEY || ""`, which will call `posthog.init("")` in environments where the variable isn't set — PostHog's SDK no-ops but emits a console warning in development.

The index route at `/` renders nothing and fires a `navigate({ to: '/stations', replace: true })` inside `useEffect`. This introduces a visible blank frame on `/`. TanStack Router supports `beforeLoad` with `throw redirect(...)` which handles this at the router level before the component mounts:

```ts
const indexRoute = createRoute({
    getParentRoute: () => rootRoute,
    path: "/",
    beforeLoad: () => { throw redirect({ to: '/stations' }) },
});
```

## Data fetching: ConvexHttpClient polling trade-off

The hooks in `src/hooks/useStations.ts`, `useCameras.ts`, and `useWaterLevelHistory.ts` all use a singleton `ConvexHttpClient` that fires one-shot HTTP requests — there's no subscription. Combined with `staleTime: 30_000` in the query client config, the app effectively polls every 30 seconds when a component re-mounts or the window refocuses. Water level data updates every ~15 minutes on the backend, so the 30-second stale window is unlikely to be a practical problem, but the real-time push behavior from the original Convex `useQuery` is gone. This means if JPS pushes an emergency alert-level change, the user won't see it for up to 30 seconds (or longer if their tab is idle).

## Netlify proxy function hardening gap

The proxy function at `netlify/functions/proxy-image.ts` fetches from a plain HTTP URL (`http://infobanjirjps.selangor.gov.my/InfoBanjir.WebAdmin/CCTV_Image/${id}.jpg`), reads the full response into memory as an `ArrayBuffer`, base64-encodes it, and returns it. There's no validation on the `id` parameter — it's used directly in a URL path. An attacker could pass path traversal characters, though the HTTP server on the other end would likely just return a 404. Adding a regex validation for the ID format (alphanumeric + limited characters) would harden the endpoint against SSRF-adjacent misuse. There's also no response-size guard beyond Netlify's default function timeout (10 seconds).

## Bundle size and code-splitting

All four route components are eagerly imported at the top of `routeTree.gen.ts`, which means Vite bundles everything into a single chunk. TanStack Router supports `lazyRouteComponent()` for per-route splitting:

```ts
const stationsRoute = createRoute({
    getParentRoute: () => rootRoute,
    path: "/stations",
}).lazy(() => import('./routes/stations/index').then(m => ({ component: m.StationsRoute })));
```

This would reduce initial load for users who land on one route and never visit others. The cameras route in particular includes significant fullscreen modal logic that most users won't need on first load.

## Dead code and naming inconsistencies

`useStationDetail` in `src/hooks/useStations.ts` is exported but never imported anywhere — the detail page (`$id.tsx`) fetches the full stations list via `useStations()` and finds the station by ID client-side. The hook is dead code that should be removed or used.

The file `src/routeTree.gen.ts` is named as though it's auto-generated by TanStack Router's codegen plugin, but is manually maintained. If someone adds the codegen plugin later, it will overwrite this file. Rename to `routeTree.ts` or add a comment at the top.
