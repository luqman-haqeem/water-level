# Staleness display, filter-count reconciliation, dead-UI removal, and sparkline scaling

Four R1 issues resolved in a single commit: stale stations (>45 min old) now render grey badges instead of severity colors, the filter dialog and detail-page navigation count/navigate only the filtered station set, the Apply/Cancel/auto-hide dead code is stripped, and `MicroTrendChart` scales its y-axis to the station's normal→danger range instead of local min/max.

Watch for: the detail page's filtered navigation list doesn't replicate the sort order from the list page, so prev/next order may diverge from what the user sees in the list (confirmed). The `alertLevelStats` fix only accounts for the offline filter but not other active filters, which is arguably intentional but worth confirming as a deliberate choice (likely).

**Verdict**: APPROVED

## High-level view

The staleness gate is a testable utility (`isStale`) that returns true when `updatedAt` is undefined or older than 45 minutes. Both `StationCard` and the detail page override the alert badge to `-1` (grey) when stale. The display logic is purely frontend; no backend changes beyond deleting a stale comment.

Filter-count reconciliation imports `useFilter` into the detail page and re-applies every filter dimension to the station list used for prev/next navigation. The filter dialog's `alertLevelStats` is narrowed to respect `showOfflineStations`. The `onFilterChange` prop is removed since filters propagate through context.

The Apply/Cancel button removal and bottom-nav scroll-listener deletion are straightforward dead-code removal with no behavioral side-effects.

The sparkline fix adds `normalLevel`/`dangerLevel` props to `MicroTrendChart`, uses them as y-axis bounds when present and non-zero, clamps data points to that range, and falls back to local min/max otherwise.

## Detail-page filtered navigation misses sort order

The list page in `index.tsx` runs a full sort pass after filtering — by name, water level, last updated, district, or geolocation distance, respecting `sortOrder`. The detail page (`$id.tsx`) applies the same filter predicates but never sorts; it uses whatever insertion order `useStations()` returns. When a user sorts by "nearest" on the list page, taps station #3, and presses "next," they'll land on a different station than the next-nearest. Confirmed by reading both files: `$id.tsx` lacks any `.sort()` call.

Extracting a shared `useFilteredStations()` hook that applies both filter and sort from `advancedFilters` would close the gap and DRY up the duplicated filter logic currently split between `index.tsx` and `$id.tsx`.

## `alertLevelStats` scope choice

The stats in `AdvancedFilter.tsx` now filter by `showOfflineStations` but still count across all districts and alert levels even when other filters are active. The alert-level pill counts don't change when you select a district, while the footer "N results" count does apply all filters. This asymmetry may be intentional UX (showing system-wide severity distribution) but the two numbers in the same dialog will diverge, which could confuse users.

## Sparkline threshold edge case

```
hasThresholds = normalLevel !== undefined && dangerLevel !== undefined
    && !(normalLevel === 0 && dangerLevel === 0)
```

If `normalLevel > dangerLevel` (misconfigured station data), `range` goes negative. The `|| 1` fallback only catches the zero case. This would produce an inverted chart. Extremely unlikely with real data, but a `Math.abs(range) || 1` or a swap guard would make it robust.

## Test coverage gaps

Six unit tests cover `isStale` including boundary, numeric, and undefined cases with fake timers. Not tested: the rendering integration — that `StationCard` and `$id.tsx` actually pass `-1` to the badge and apply the destructive class when `isStale` returns true. This would require component-level render tests.
