# Per-station tag notifications — v2 review

All five issues from the v1 review have been addressed: OneSignal initialization relocated to a dedicated `OneSignalProvider` component wrapping the app shell, a `reconcileTagsWithLocalStorage` function added and called post-init, the dialog now renders station names from `{id, name}` tuples stored in localStorage, retained dead code is documented with `[RETAINED FOR FUTURE USE]` comments, and the backend test gap is acknowledged in a file header note. The implementation is coherent and the test suite (58 tests) exercises the critical paths.

Watch for: Concurrent `subscribeToStation` calls can corrupt localStorage because each call reads, mutates, and writes the JSON array without synchronization (confirmed). The `reconcileTagsWithLocalStorage` function re-adds tags sequentially without per-iteration error isolation — one failure aborts the remaining re-pushes (confirmed).

**Verdict**: APPROVED

## High-level view

Tag reconciliation handles both drift directions at startup, but the sequential `addTag` loop means a single failure in the middle abandons remaining stations. The next page load retries, so this is self-healing but slow to converge if OneSignal is intermittently rejecting calls.

The concurrent-write race in `notificationService` is the remaining structural concern: `subscribeToStation` and `unsubscribeFromStation` both read localStorage, mutate in memory, then write back. Two calls in flight simultaneously will each read the same snapshot and the last write wins, potentially dropping a subscription. The `useStationSubscription` hook serializes via `await` so single-station rapid toggle is safe, but multiple independent hooks firing in parallel (e.g., a future "subscribe all" action) would hit this race.

## localStorage read-modify-write race

The service functions follow a pattern:

```ts
const stations = getSubscribedStations(); // reads & parses localStorage
stations.push({ id, name });              // mutates in memory
saveSubscribedStations(stations);          // JSON.stringify & setItem
```

`localStorage.setItem` is synchronous, but the surrounding function is `async` and yields to OneSignal before the save has any effect on future readers. If two `subscribeToStation("A", ...)` and `subscribeToStation("B", ...)` calls execute before either's `saveSubscribedStations` is reached by the other, both read the same initial snapshot. Whichever saves last overwrites the other's addition.

In practice this is mitigated by the hook's `await` pattern — a single card's subscribe/unsubscribe/subscribe sequence is serial. The race manifests only when multiple independent hooks fire simultaneously, such as a hypothetical "subscribe all visible" action or a user tapping two cards in quick succession on a fast device.

## Reconciliation partial-failure isolation

```ts
for (const station of localStations) {
    const tagKey = `station_${station.id}`;
    if (!osTags[tagKey] || osTags[tagKey] !== "true") {
        await OneSignal.User.addTag(tagKey, "true"); // throws → skips rest
    }
}
```

If `addTag` rejects for one station (rate limit, network blip), the exception propagates to the outer `catch`, abandoning the loop. Remaining stations never get their tags re-added until the next page load triggers reconciliation again. Wrapping each `addTag` call in its own try/catch or using `Promise.allSettled` would decouple individual failures from the overall reconciliation attempt.
