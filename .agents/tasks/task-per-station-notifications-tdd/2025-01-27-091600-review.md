# Per-station push notification subscriptions via OneSignal Data Tags

Replaces broadcast-style danger notifications with per-station opt-in targeting. The frontend gains a bell icon on each `StationCard` that sets/removes a OneSignal tag (`station_{id}: "true"`) and persists state to localStorage for optimistic UI. The backend `notifyDangerForStation` now sends via the OneSignal `filters` API (tag match) instead of `included_segments: ["Subscribed Users"]`. A full Vitest + React Testing Library infrastructure was stood up (51 tests across 6 files) following TDD.

Watch for: localStorage and OneSignal tags can drift silently (confirmed — no reconciliation path exists). The `NotificationHandler` dialog displays raw Convex document IDs instead of station names (confirmed). OneSignal initialization is no longer performed anywhere in the new code (confirmed — the init call from the old `NotificationHandler` was removed and not relocated).

**Verdict**: NEEDS_CHANGES

## High-level view

The notification service uses a localStorage-first, OneSignal-second strategy: mutations always land in localStorage regardless of SDK state, and any OneSignal failure is swallowed with a `console.warn`. This gives instant UI but creates a one-way sync: the client can fall out of step with the OneSignal backend, and there's no recovery mechanism to detect or fix the drift.

OneSignal SDK initialization (`OneSignal.init(...)`) previously lived in the `NotificationHandler` component. That component was gutted and now only reads localStorage. The `init` call was not moved elsewhere, meaning `addTag`/`removeTag` will always throw in a fresh session and the service will silently fall back to localStorage-only. Push subscriptions will never actually reach OneSignal unless init is performed somewhere upstream.

The dialog that shows subscribed stations renders `"Station {stationId}"` where `stationId` is the Convex document ID (e.g., `k573f8xyz123`). Users see opaque identifiers rather than human-readable station names, making the subscription management screen unusable for its intended purpose.

The backend replaced `included_segments` with a `filters` array and removed the per-user favorites loop. Dead code remains: `getRecentNotification` and `recordNotification` reference the old per-user model and are no longer called anywhere.

No test exercises the actual `notifyDangerForStation` action handler's control flow (cooldown → fetch → record), so regressions in that orchestration path won't be caught. Cross-tab localStorage synchronization is also untested and unimplemented (no `storage` event listener).

## OneSignal initialization gap

The old `NotificationHandler` contained the app's only `OneSignal.init({ appId })` call, guarded by a module-level `oneSignalInitialized` flag. The new version of that component imports only `getSubscribedStations` and `unsubscribeFromStation` — no SDK usage at all. The bell icon in `StationCard` calls `OneSignal.User.PushSubscription.optIn()` and `OneSignal.User.addTag(...)` via `notificationService.ts`, but those methods require the SDK to have been initialized first.

Without init, every `subscribeToStation` call hits the catch block:

```ts
} catch (error) {
    console.warn(
        "[notificationService] OneSignal operation failed, localStorage updated:",
        error
    );
}
```

The user sees a filled bell (localStorage says subscribed), but no push tag is ever set on the OneSignal device record. The notification will never be delivered.

## localStorage–tag drift and its consequences

The design is optimistic by intention: write localStorage first, sync OneSignal second. But "sync" is fire-and-forget. If `addTag` fails — due to missing init, network error, or quota — no retry occurs and no warning reaches the user. Conversely, if a user clears browser data, localStorage resets to empty while the OneSignal backend still holds the tags. There's no startup path that calls `getTags()` to reconcile.

For a notification-critical feature (danger alerts for water levels), silent failures mean a user believes they'll be alerted but won't be.

## Subscription dialog usability

`NotificationHandler` iterates `getSubscribedStations()` (an array of strings) and renders:

```tsx
<span className="text-sm">Station {stationId}</span>
```

Since station IDs are Convex document IDs (opaque hashes), the dialog is unreadable. Either the storage format should be enriched to `{ id, name }` tuples, or the dialog should query station names from the Convex backend at open time.

## Dead per-user notification code

`getRecentNotification` (requires `userId` + `stationId`) and `recordNotification` (writes a per-user entry) remain exported and unused. They reference the old per-user model and are no longer called by `notifyDangerForStation` or any other function. If they're kept for future use, that should be documented; otherwise they're dead code that obscures the current design.

## Test gaps

The full `notifyDangerForStation` action handler execution (cooldown → build → fetch → record) is not exercised by any test. The mitigation (extract pure functions) is reasonable given Convex runtime limitations, but the orchestration between those functions and the Convex context (`runQuery`, `runMutation`, `fetch`) is where regressions most likely emerge.

Cross-tab localStorage synchronization: if a user subscribes in one tab, another open tab's `useStationSubscription` hook won't re-render because there's no `storage` event listener. This is an unimplemented feature with no test coverage.
