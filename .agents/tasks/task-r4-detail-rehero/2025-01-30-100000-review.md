# Detail page re-hero with gauge-first layout and data-coloured cards

The change restructures the station detail page from a card-wrapped, collapsible-section layout into a flat, content-first design where the water level number dominates and the gauge/chart render directly without accordion wrappers. Simultaneously, `StationCard` drops the `border-l-4` severity pattern in favour of tinted backgrounds and coloured text on the level value itself. The gauge's `animate-pulse` is narrowed to fire only at danger level.

Watch for: `getThresholdDelta` uses raw float arithmetic whose edge-case behaviour at exact boundary values may confuse users (confirmed). The `bg-alert/5` opacity syntax requires Tailwind's arbitrary-value support for opacity modifiers — verify the build output actually applies the intended tint (likely).

**Verdict**: APPROVED

## High-level view

The StationCard shifts from a "coloured border marks severity" approach to "tint the card background and colour the data value." Normal-state cards carry no visual decoration — only elevated states get attention. The `opacity-60` treatment for stale/unknown cards is a stronger visual suppression than the old muted border, potentially making them feel non-interactive on touch devices.

The detail page removes the ExpandableSection accordion that hid the gauge and chart behind a tap. Content now flows top-to-bottom: staleness banner → hero number (severity-coloured, with plain-language delta) → horizontal gauge → trend chart → vertical threshold list → camera.

The `getThresholdDelta` helper computes a human-readable distance string. Its cascade is correct for the four zones but has an asymmetry at exact threshold boundaries: only danger gets "At or above" treatment; the others surface "0.00m below X."

The gauge animation fix is minimal and correct: two `animate-pulse` class applications now additionally gate on `currentLevel >= levels.danger`.

## StationCard opacity and Tailwind modifier risk

`bg-alert/5` uses Tailwind's colour-with-opacity shorthand. This works because the CSS vars use space-separated HSL values (e.g., `35 92% 50%`). The `/8` and `/10` modifiers set 8% and 10% alpha. Tailwind v3.1+ with JIT supports arbitrary opacity values, but `/8` is not a standard step in the default scale (0, 5, 10, 20…). With Vite's JIT compilation this should generate correctly, but if the project ever moves to a safelist or pre-built approach, these become dead classes.

The `opacity-60` applied to stale or unknown-level cards dims the entire card including station name, metadata, and interactive affordances. Unlike the old `border-l-muted-foreground/30` which only affected the left border, this blanket dim could make stale cards appear disabled rather than merely stale — particularly on mobile where hover states don't reinforce interactivity.

## Plain-language threshold delta boundary asymmetry

`getThresholdDelta` cascades from danger downward. When `level === danger`, the first condition (`level >= danger`) fires and produces "At or above Danger level." But when `level === warning`, the second condition fires and produces `(danger - level).toFixed(2) + "m below Danger"` — which evaluates to "0.00m below Danger" if danger equals warning (unlikely but schema-possible) or to the correct distance otherwise.

The real asymmetry: only the danger boundary gets "At or above" language. A station sitting exactly at the warning threshold sees "0.00m below Danger" rather than "At Warning level." This is a UX confusion point, not a bug — the math is correct but the human interpretation is wrong. Adding equality checks (`level === warning → "At Warning level"`) before the distance calculations would eliminate the issue.

## Duplicated severity-colour logic

`getHeroLevelColor` in the detail page and `getLevelColor` in StationCard are identical switch statements. Two call sites don't warrant extraction, but if a third appears (e.g., a notification card), a shared `getSeverityTextColor(alertLevel, stale)` utility would prevent drift.
