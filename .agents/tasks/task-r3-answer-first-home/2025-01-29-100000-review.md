# Answer-first home with status summary, watched stations, and nearest default

This change restructures the station list page to answer "is anything wrong?" before presenting the full list. A tappable status summary strip shows station counts by severity, a "My Stations" section pins subscribed stations at the top, a "Needs Attention" section surfaces non-normal stations, and the default sort flips to "nearest" so the closest stations appear first. The pull-to-refresh (which did nothing real) and the redundant page title are removed.

Watch for: Clicking the "no data" segment in the status strip will show zero results because the filter value `-1` never appears in the alertLevel filtering pipeline (confirmed). The "My Stations" and "Needs Attention" cards duplicate in the main grid below (confirmed). Subscribed station IDs are read from localStorage once on mount and never refresh if the user subscribes/unsubscribes during the session (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The "no data" segment in StatusSummary uses a synthetic filter value (`-1`) that the downstream filter logic doesn't recognize — it always defaults missing alert levels to `'0'`, so clicking "no data" produces an empty result set.

Stations pinned in "My Stations" and "Needs Attention" also appear in the main grid below because `filteredStations` is never de-duplicated against the pinned sections. On a phone, the same station card appears twice on screen.

The default sort change to `'nearest'` requests geolocation unconditionally on mount. The location indicator bar is always visible when `sortBy === 'nearest'`, which is now every first load — after location resolves, the bar says "Sorting by distance from your location" permanently, consuming ~48px of vertical space that competes with the answer-first goal.

## "No data" filter value disconnected from filter pipeline

`StatusSummary` categorizes stations with stale or missing data into a "no data" bucket and maps it to `filterValue: '-1'`. When tapped, this sets `advancedFilters.alertLevels` to `['-1']`. In the filtering code within `stations/index.tsx`:

```typescript
const alertLevel = station.current_levels?.alert_level || "0";
if (!alertLevelMap.has(alertLevel)) {
    alertLevelMap.set(alertLevel, []);
}
alertLevelMap.get(alertLevel)!.push(station);
```

Stations with missing or null `alert_level` are bucketed under `'0'` (normal). The `alertLevelMap` never contains a `-1` key. Similarly in `AdvancedFilter.tsx`:

```typescript
filtersToApply.alertLevels.includes(station.current_levels?.alert_level || '0')
```

Both places fall back to `'0'`. So filtering by `'-1'` matches nothing.

Fix options: add special handling in `applyAdvancedFilters` to treat `-1` as "station where `isStale(updated_at)` is true or `alert_level` is null/undefined", or stop making the "no data" segment tappable (just informational).

## Card duplication between pinned sections and the main grid

`needsAttentionStations` excludes stations already in `myStations`, but neither section's stations are removed from `filteredStations`. On a typical load with subscriptions and a station at Warning level, the user sees the same card in a pinned section and again 2-3 cards down in the main grid. This UX redundancy undermines the "answer-first" goal — the user may think the card appearing twice means something different.

## Subscription state frozen on mount

```typescript
const subscribedIds = useMemo(() => getSubscribedStationIds(), []);
```

`getSubscribedStationIds()` reads `localStorage` synchronously. The empty dependency array means this never re-runs. If the app uses client-side navigation (TanStack Router) and the user navigates to a station detail, taps the notification bell, then navigates back, the station route component may not remount — React reuses it. The "My Stations" section will be stale until a full page reload.

A lightweight fix: listen for `storage` events, or re-read on route focus via a `useEffect` keyed to a navigation event.

## Location indicator always visible

The location status indicator renders whenever `advancedFilters.sortBy === "nearest"`, which is now the default. After location resolves, the bar reads "Sorting by distance from your location" — always-present chrome on mobile that occupies ~48px above the stations. Suppress the bar once `location.coordinates` is populated; show it only during loading/error states.
