# Danger-level push notifications via OneSignal (v2)

This change adds push notification infrastructure for water-level danger alerts. When a station's alert level transitions from below 3 to exactly 3, the Convex backend schedules a OneSignal broadcast to all push subscribers, gated by a 1-hour per-station cooldown. The frontend provides a bell icon that opens a dialog for toggling push subscription via the OneSignal browser SDK. This is a v2 pass after fixes addressing per-user/broadcast mismatch, unused `updatedAt`, OneSignal re-init, and the acknowledged-intentional users gap.

Watch for: broadcast delivery scope still misaligned with favorites model (confirmed); station cooldown ineffective when no users have favorited (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The notification flow is now coherent at the station level: `waterLevelUpdater` detects a rising transition, schedules `notifyDangerForStation`, which checks a per-station cooldown via `getRecentStationNotification` before broadcasting. The per-user cooldown remains as secondary record-keeping for future per-user targeting but no longer gates delivery.

The remaining architectural tension is that delivery is a broadcast to all OneSignal subscribers (`included_segments: ["Subscribed Users"]`), but the favorites table implies per-station subscriptions. A user who subscribed to push but hasn't favorited any station still receives every alert. A user who favorited only one station receives alerts for all stations. The favorites model is dead weight in the delivery path — it only gates cooldown log recording.

The station cooldown check depends on finding a `notificationLog` record for the station within the last hour. But `notificationLog` entries are only written in the per-user loop — if `userIds` is empty (no one favorited the station), no record is written, the cooldown never engages, and every threshold crossing fires a broadcast. With zero users in the system today, this means every station crossing danger level will broadcast on every data sync cycle that re-detects the transition.

## Cooldown bypass path

The station cooldown relies on `getRecentStationNotification`, which queries `notificationLog` with index `by_station`. The only writer is `recordNotification`, called inside:

```typescript
for (const userId of userIds) {
  const recent = await ctx.runQuery(
    internal.notifications.getRecentNotification,
    { userId, stationId }
  );
  if (!recent) {
    await ctx.runMutation(internal.notifications.recordNotification, {
      userId, stationId, alertLevel: 3,
    });
  }
}
```

When `userIds` is empty (which is always the case today since there's no user creation endpoint), this loop is a no-op. No `notificationLog` row is inserted. On the next data sync that observes `alertLevel === 3` after a brief dip below 3, the transition detector fires again, the cooldown check finds nothing, and another broadcast goes out.

The stale-data edge case compounds this: if the scraper returns data causing the level to briefly drop and rise again within the cooldown window, the transition detector fires but the per-station cooldown would normally block it — except with no cooldown record, repeated broadcasts occur.

The fix: after sending the OneSignal notification, unconditionally insert a cooldown sentinel — either a dedicated `stationCooldownLog` table or a `notificationLog` entry with a synthetic/system user ID.

## Broadcast vs. favorites model mismatch

The schema has a `favoriteStations` table with `by_user`, `by_user_station`, and `by_station` indexes, and the action queries it to find users who favorited the station — yet the actual delivery doesn't use this information at all. Every push subscriber receives every station's alert.

This is a valid design choice for an MVP (all subscribers get all alerts), but then the favorites query and the user-loop recording logic are dead code in the notification path. They exist only as scaffolding for future per-user targeting. The concern is that this isn't documented or obvious from the code — a reader would reasonably expect the favorites query to gate delivery.
