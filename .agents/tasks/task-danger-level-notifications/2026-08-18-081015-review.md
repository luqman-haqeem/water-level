# Danger-level push notifications via OneSignal

This change adds push notification infrastructure for water-level danger alerts. When a station's alert level rises from below 3 to exactly 3, the Convex backend schedules a OneSignal notification to all subscribed users who favorited that station, gated by a 1-hour per-user-per-station cooldown. The frontend adds a bell icon in the header that opens a dialog for toggling push subscription via the OneSignal browser SDK.

Watch for: notification targeting mismatch between per-user cooldown logic and broadcast delivery (confirmed); missing `updatedAt` arg in the `notifyDangerForStation` handler body (confirmed); OneSignal `init()` called on every mount with no idempotency guard (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The notification backend splits across three Convex modules: `favorites.ts` provides a query to find users who favorited a station, `notifications.ts` handles cooldown checks and OneSignal delivery, and `waterLevelUpdater.ts` detects the danger transition and schedules the action.

The core design tension is between the per-user cooldown model and the actual notification delivery. The cooldown logic iterates users, records per-user sends, then fires a single broadcast to the "Subscribed Users" segment — meaning users who passed cooldown and users who didn't all receive the same push. This is a functional mismatch that needs resolution before shipping.

The frontend component initializes OneSignal inside a `useEffect` with no guard against re-initialization across re-mounts or hot reloads. The `react-onesignal` SDK's `init()` is documented as safe to call once per page load; repeated calls may throw or silently fail depending on version.

<details>
<summary>Issues (4)</summary>

1. **Broadcast vs. per-user targeting mismatch** — The cooldown logic records notifications per-user, but `notifyDangerForStation` sends to the `included_segments: ["Subscribed Users"]` broadcast segment. Users on cooldown still receive the push. Either target by OneSignal `external_user_id` (requires mapping Convex user IDs to OneSignal player IDs) or remove per-user cooldown and use a per-station cooldown instead.
2. **`updatedAt` arg declared but unused** — `notifyDangerForStation` accepts `updatedAt: v.optional(v.string())` in its args but the handler destructures only `{ stationId, currentLevel }`. The value is passed from the scheduler but silently dropped. Either use it in the notification message or remove it from the action's arg schema.
3. **OneSignal init() called on every mount** — `NotificationHandler.tsx` calls `OneSignal.init({ appId })` inside a `useEffect` with `[appId]` deps. If the dialog is opened, closed, and reopened, the effect runs again. Move initialization to a top-level provider or add a module-level flag to prevent re-init.
4. **No `users` management endpoint** — The schema defines a `users` table and `favoriteStations` references `v.id("users")`, but there is no mutation to create user records or manage favorites. The notification pipeline will find zero users until those are implemented. This may be intentional (deferred to a later PR), but it means the feature is inert as shipped.

## Notification targeting: broadcast vs. per-user cooldown

The `notifyDangerForStation` action implements per-user cooldown logic: it iterates each user who favorited the station, checks `getRecentNotification` for a 1-hour window, and only sets `shouldSend = true` if at least one user hasn't been notified recently. It then records a `notificationLog` entry for each non-cooled-down user.

However, the actual OneSignal API call uses `included_segments: ["Subscribed Users"]`, which is a broadcast to all push subscribers regardless of which Convex user they are. The per-user cooldown gates whether the push fires at all, but when it does fire, every subscriber receives it — including those on cooldown. The `notificationLog` records become inaccurate because they imply targeted delivery.

To fix this properly, the action needs to either:
- Use OneSignal's `include_aliases` or `include_player_ids` to target specific users (requires storing OneSignal player IDs in the `users` table), or
- Simplify to a per-station cooldown (one `notificationLog` per station, ignore user dimension) since the delivery is broadcast anyway.

## Danger transition edge case

The transition detection skips notification when there's no existing `currentLevels` record for a station (`previousAlertLevel` is `undefined`). If the first data point for a station arrives at danger level, no notification fires. This is likely the right behavior for initial data population but means a station added to the system mid-flood won't trigger alerts until it drops below danger and rises again.

## OneSignal frontend initialization

```typescript
useEffect(() => {
    if (!appId) { setIsLoading(false); return; }
    const initOneSignal = async () => {
        try {
            await OneSignal.init({ appId });
            setIsInitialized(true);
            // ...
        }
    };
    initOneSignal();
    // ...
}, [appId]);
```

The `react-onesignal` package wraps the Web Push SDK. Its `init()` registers the service worker and creates the OneSignal iframe. Calling it multiple times can produce console errors or duplicate service worker registrations. Since the `NotificationHandler` component mounts/unmounts with dialog open state, each open triggers the effect. A module-level `let initialized = false` guard or lifting init to `App.tsx` would prevent this.

## `updatedAt` parameter gap

The scheduler call in `waterLevelUpdater.ts` passes `updatedAt`:

```typescript
await ctx.scheduler.runAfter(0, internal.notifications.notifyDangerForStation, {
    stationId, currentLevel, updatedAt
});
```

But the action handler destructures only `{ stationId, currentLevel }`:

```typescript
handler: async (ctx, { stationId, currentLevel }) => {
```

The `updatedAt` value (a string like "2024-01-15 08:30") is available in `args` but never used. It could be included in the notification body to tell the user when the reading was taken.
